# EventMap — Импорт афиши (холодный старт контента)

> Техническая заметка к шагу 1 стратегии холодного старта (см. [COMPETITORS.md](./COMPETITORS.md)). Задача: карта Астаны **никогда не пустая** ещё до прихода живых организаторов. Решение — агрегировать публичную афишу из внешних источников, нормализовать в схему события EventMap и показывать как слой «из афиши», с апгрейдом до «живого», когда организатор заберёт карточку себе.

---

## 1. Цель и принцип

- На карте всегда есть события «скоро» в целевом городе, даже при нуле зарегистрированных организаторов.
- Импортированные события визуально и по правам отличаются от «живых» (`source`-метка, нет live-видео, ниже `importance`).
- Когда реальный организатор подтверждает («claim») событие/площадку — карточка переходит из `afisha` в `organizer`, получает полные возможности (видео, билеты, редактирование).

---

## 2. Источники

| Источник | Тип | Что берём | Примечание |
|---|---|---|---|
| **Ticketon (ticketon.kz)** | афиша + билеты | концерты, стендап, кино, спорт | самый плотный по КЗ; есть гео/площадки |
| **Sxodim (sxodim.com/astana)** | гид «куда сходить» | события, места, акции | хорош по «небилетным» активностям |
| **Сайты площадок** | первоисточник | расписание конкретных венью | точные время/адрес |
| **Instagram-паблики / Telegram-каналы** | соц. | анонсы локальных ивентов | шумно, нужна ручная курация |

> ⚠️ **Юридически.** У Ticketon/Sxodim, как правило, нет публичного API — данные на публичных страницах. Перед парсингом проверить `robots.txt` и ToS, ограничить частоту, кэшировать, указывать источник и ссылку, не копировать билетную продажу. На старте безопаснее **партнёрство/договорённость об отдаче фида**, а не «тихий» скрейп. Для соцсетей — только публичные посты, с атрибуцией.

## 3. Архитектура ingestion

Отдельный фоновый сервис (не в основном API, чтобы парсинг не ронял прод):

```
[Source adapters] → [Normalizer] → [Geocoder] → [Dedup] → [events.source='afisha']
   Ticketon                                                      │
   Sxodim          каждый адаптер знает,                          ▼
   Venue feeds     как достать сырьё из                    основная БД EventMap
   (cron, N×/день) своего источника                        (та же таблица events)
```

Поток:
1. **Source adapter** — на каждый источник свой модуль: тянет сырьё (HTML/feed) и отдаёт «сырые» записи. Запускается по расписанию (например, каждые 3–6 ч; «сегодня/завтра» — чаще).
2. **Normalizer** — приводит к единой `RawEvent` → к схеме `events` EventMap (title, description, startAt/endAt, category-маппинг, price, cover).
3. **Geocoder** — превращает адрес/название места в `lat/lng` (Mapbox Geocoding / собственный справочник площадок). Без координат событие на карту не попадает — кладём в очередь «требует гео».
4. **Dedup** — одно событие может быть в двух источниках → схлопываем (см. §5).
5. **Upsert** в `events` с пометкой источника.

Адаптеры изолированы: падение парсера Ticketon не ломает Sxodim. Для устойчивости к смене вёрстки — снапшоты «сырья» и алерт при резком падении числа записей.

## 4. Метки в данных: «из афиши» vs «живое»

Расширить таблицу `events` (к схеме из [API_CONTRACT.md](./API_CONTRACT.md)) полями происхождения:

```sql
ALTER TABLE events ADD COLUMN source        TEXT NOT NULL DEFAULT 'organizer';
                                              -- 'afisha' | 'organizer' | 'user'
ALTER TABLE events ADD COLUMN source_name    TEXT;        -- 'ticketon' | 'sxodim' | ...
ALTER TABLE events ADD COLUMN source_url     TEXT;        -- ссылка на первоисточник (атрибуция)
ALTER TABLE events ADD COLUMN source_ref     TEXT;        -- внешний id для идемпотентного upsert
ALTER TABLE events ADD COLUMN is_claimed     BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE events ADD COLUMN imported_at    TIMESTAMPTZ;
CREATE UNIQUE INDEX ux_events_source_ref ON events(source_name, source_ref)
    WHERE source_name IS NOT NULL;   -- идемпотентность импорта
```

В API карточка события отдаёт это в ответе (дополнение к существующему JSON):

```jsonc
{
  "id": "...", "title": "Стендап-вечер", "status": "soon",
  "source": "afisha",            // afisha | organizer | user
  "sourceName": "ticketon",
  "sourceUrl": "https://ticketon.kz/...",
  "isClaimed": false
}
```

### Различия в продукте

| Аспект | `afisha` (импорт) | `organizer` / `user` (живое) |
|---|---|---|
| Пин на карте | приглушённый, бейдж «Афиша» | полноцветный, анимация категории |
| `importance` (вес пина, ADR-002) | base − штраф (ниже в выдаче) | полный вес |
| Live-видео, «Я тоже здесь» | нет | да |
| Билеты | ссылка на источник (`sourceUrl`) | нативная покупка (P) |
| Редактирование | только модерация | владелец |
| Карточка | плашка «Данные из {source} · открыть оригинал» | полная |

В клиенте (`feature/event` / `feature/map`) добавить `source` в `EventDetail`/`MapEvent` и ветку отрисовки: для `afisha` — бейдж и кнопка «Открыть на {source}» вместо «Купить билет».

## 5. Дедупликация

Одно и то же событие из разных источников → схлопнуть, иначе на карте дубли.

Ключ совпадения (fuzzy): нормализованный `title` + дата (день) + близость координат (< ~150 м) + площадка. Стратегия:
- если есть `organizer`-версия → она главная, `afisha` прячем (или линкуем);
- среди `afisha` — оставляем источник с более полными данными (есть гео, цена, обложка);
- хранить связь дублей, чтобы при claim не потерять.

---

## 6. Жизненный цикл и «claim»

1. Импорт создаёт `afisha`-события (`is_claimed=false`).
2. Организатор регистрируется, находит свою площадку/событие → **запрос на подтверждение** (проверка: домен почты, код на сайте площадки, ручная модерация).
3. После подтверждения — `source='organizer'`, `is_claimed=true`, владелец получает полные права; будущие импорты по этому `source_ref` не перетирают живые данные.
4. **Протухание:** `afisha`-события чистим по `endAt` (карта показывает только актуальное — принцип из [MAP_CONCEPT.md](./MAP_CONCEPT.md)); неактуальные импорты удаляем/архивируем.

---

## 7. Качество и модерация

- Минимальный порог: у события должны быть `title`, `startAt`, координаты — иначе не публикуем на карте.
- Чёрный список категорий/слов; ручная очередь для соц-источников.
- Атрибуция обязательна (ссылка на источник) — и юридически, и этически.
- Метрика здоровья импорта: число свежих `afisha`-событий с гео в Астане на ближайшие 24–48 ч (то самое «карта не пустая»).

---

## 8. Порядок внедрения (MVP-приоритет)

1. Поля `source*` в БД + отдача в API + бейдж «Афиша» в клиенте.
2. Один адаптер (Ticketon) + геокодер + upsert по `source_ref` — этого уже хватает, чтобы карта ожила.
3. Cron-расписание + алерт на падение объёма.
4. Sxodim-адаптер, дедуп.
5. Claim-флоу для организаторов.

> Начни с одного источника и одного города. Цель не «импортировать всё», а сделать вечернюю карту Астаны плотной — остальное наращивается адаптерами без изменения ядра.
