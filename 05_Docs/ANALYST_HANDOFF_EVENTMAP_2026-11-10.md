## 1. Суть продукта и аудитория

**EventMap — живая карта интересов города: что происходит, кому это интересно и к чему можно присоединиться.**

Центр идеи — не каталог мероприятий сам по себе, а связь людей, интереса, места и времени. Это интерес всего города, не только друзей пользователя.

Основная цепочка:

> Увидел на карте → заинтересовался → присоединился → пришёл → подтвердил происходящее → поделился моментом → открыл новое место.

### 1.1. Какие активности должны помещаться в продукт

| Источник / сценарий | Примеры | Что важно пользователю |
| --- | --- | --- |
| Организатор | Концерт, выставка, фестиваль, лекция | Дата, программа, источник, билет, реальная обстановка |
| Спортивный организатор | Матч, турнир, марафон, массовый забег | Участие, ограничения, место; для забега — маршрут и дистанция |
| Магазин или бизнес | Открытие, мастер-класс, временная акция, промоквест | Что происходит именно сейчас, коммерческая маркировка |
| Городская организация | День города, общественное мероприятие, официальное объявление | Проверенный источник и актуальность |
| Частный инициатор | Арендовал поле, ищет игроков; прогулка; настольные игры | Свободные места, требования, стоимость, порядок вступления |
| Очевидец | Телескоп во дворе, уличная музыка, запуск дронов | Где, насколько свежо, сколько независимых подтверждений |
| Временный продавец | Арбузы с машины, мороженое, ярмарочная точка | Кто продаёт, где и до какого времени; не постоянная карточка магазина |
| Закрытая группа | Свадьба, день рождения, частная встреча | Приглашения, RSVP, непубличный адрес и альбом гостей |

Официальное уведомление о выборах — возможный информационный сценарий проверенного источника. Организация голосования, сбор бюллетеней и подтверждение избирательных прав в продукт не включены.

### 1.2. Первый рынок и ценность

Рабочий пилот — Астана, Казахстан; текущая валюта в моделях — KZT. Расширение на другие города, языки и валюты следует проектировать без жёстких предположений в данных.

Для жителя: найти живую активность и людей с общим интересом. Для инициатора: собрать группу. Для организации: получить участников и обратную связь. Для города: показать агрегированный интерес без раскрытия перемещений отдельных людей.

Главная продуктовая метрика-кандидат: количество состоявшихся активностей, в которых люди участвовали через EventMap. Просмотры и XP — вспомогательные показатели.

## 2. Роли и права

Ниже — **целевая** матрица, а не описание полностью реализованной системы ролей.

| Роль | Возможности | Ограничения |
| --- | --- | --- |
| Гость | Смотреть разрешённую публичную информацию | Не публикует, не подтверждает присутствие, не получает закрытые данные |
| Пользователь | Интерес, участие, комментарии, свои фото/ролики, личные активности | Только в доступных активностях; ограничения по возрасту и доверию |
| Инициатор / автор | Создать и изменить свою активность, управлять заявками | Не назначает себе официальный статус, не накручивает независимые подтверждения |
| Участник | Вступить, отменить участие, пройти чек-ин, добавить разрешённый контент | Участие не равно физическому присутствию; права определяет сервер |
| Представитель организации | Подать заявку на проверку, вести активности организации | Права делегированы организацией; до проверки нет знака аккредитации |
| Аккредитованная организация | Официальные публикации, разрешённые промоквесты и брендированные маркеры | Аккредитация не освобождает от модерации конкретного контента |
| Официальный городской источник | Публикации от учреждения / города | Ручная проверка полномочий; отдельные правила для чувствительных объявлений |
| Модератор | Проверить жалобы, документы, активности и медиа | Только назначенные полномочия, обязательная причина решения и журнал |
| Администратор | Управление ролями, доступом, справочниками и настройками | Персональная учётная запись, аудит; не общий ключ для всей команды |

Сегодня бизнес-аккаунт привязан к одному пользователю; полноценная команда организации и детальные роли сотрудников не подтверждены реализацией. Подтверждение телефона также нельзя считать готовым: текущая регистрация — email/пароль.

## 3. Предметная модель

### 3.1. Единый контейнер активности

В продуктовой речи используем «активность», в текущем коде — `Event`. `Activity` из концепции пока не является завершённым переименованием API и БД.

Не создавать независимые несвязанные продукты для свадьбы, футбола и марафона. Общая активность содержит описание, автора, время, доступ, медиа и участие. Специализированные данные, например маршрут забега, добавляются расширением.

Нужно разделять независимые измерения:

| Измерение | Смысл | Пример |
| --- | --- | --- |
| Намерение автора | Зачем создаётся | Организую / ищу людей / вижу сейчас |
| Категория | О чём активность | Спорт / музыка / торговля / образование |
| Формат | Как проходит | Концерт / футбол / марафон / прогулка |
| Источник | Кто отвечает | Инициатор / очевидец / бизнес / организация / государственный аккаунт |
| Видимость | Кто обнаружит | Публичная / по ссылке / по приглашению |
| Вступление | Как получить участие | Открыто / по одобрению / по приглашению |
| Оплата | Как оплачивается | Бесплатно / внешняя покупка / встроенная оплата после интеграции |
| Аудитория | Для кого | Общая / семейная / взрослая, дополнительные ограничения |

В коде `kind` содержит `planned`, `gathering`, `live_signal`, `private`, а приватность также хранится в `visibility`. Это смешение нужно нормализовать с обратной совместимостью. Не добавлять `marathon` в существующий enum без анализа: предпочтительное предложение — формат спортивной активности с отдельными данными маршрута.

### 3.2. Действия, которые нельзя смешивать

- **Интересно** — хочу следить, но не обещаю прийти.
- **Участвую / иду** — принятое намерение или зарегистрированное участие.
- **Заявка** — участие ещё ожидает решения.
- **Был / чек-ин** — отметка посещения с указанным способом проверки.
- **Подтверждаю происходящее** — независимое свидетельство с места.
- **Смотрю ролик** — цифровой просмотр, не посещение.
- **Прошёл маршрут** — отдельный результат с источником доказательства; не выводится из просмотра или нажатия «иду».

Счётчики должны иметь одинаковый смысл на карте, в карточке, ленте, профиле и аналитике.

### 3.3. Базовые сущности

Пользователь; организация и заявка на аккредитацию; Event; интерес; заявка на вступление; участие; подтверждение; комментарий; медиа; приглашение и ответ гостя; уведомление; квест и прохождение; XP и достижения; посещённый район; жалоба и решение модератора.

Новые для марафонов: дистанция/маршрут активности, версия маршрута, упорядоченная геометрия, контрольная точка, регистрация участника на дистанцию. GPS-трек и спортивный результат — отдельный будущий контур, не обязательное условие первой версии.

## 4. Основные пользовательские сценарии

### UC-01. Найти занятие рядом

Пользователь открывает карту, выбирает интерес/время, открывает карточку, различает объявление автора и контент участников, отмечает интерес или вступает. Отказ в геолокации не блокирует приложение: можно выбрать район вручную.

### UC-02. Собрать людей

Автор создаёт «Ищу людей», например футбол на 10 человек; указывает стоимость, время, уровень подготовки и правило вступления. Человек подаёт заявку или занимает место. Автор видит подтверждённых участников отдельно от ожидающих. Отмена участия освобождает место по правилам события.

### UC-03. Показать происходящее сейчас

Очевидец быстро создаёт сигнал с местом, временем и необязательным медиа. При похожей активности система предлагает подтвердить существующую, а не размножает точки. Новое подтверждение повышает доверие; повтор одного пользователя не увеличивает счётчик. По окончании срока сигнал перестаёт показываться как актуальный.

### UC-04. Создать официальное событие

Представитель проверенной организации выбирает организацию-автора, публикует событие, условия участия и медиа. Статус источника выдаёт сервер. Ролики посетителей размещаются в отдельном слое «С места».

### UC-05. Провести закрытую встречу

Автор создаёт закрытую активность, отправляет приглашения, получает ответы и открывает адрес только разрешённой аудитории. Событие, гости и их медиа не попадают в публичную карту или рекомендации. Пересланная ссылка не должна обходить политику доступа.

### UC-06. Поделиться моментом

Пользователь открывает конкретную активность, выбирает фото/видео или камеру, видит превью и ход загрузки. Видео привязано к этой активности. После передачи файла отображается обработка, затем готовый ролик. При ошибке повтор не создаёт незаметный дубликат.

### UC-07. Исследовать город

Пользователь включает игровой слой, посещает новое место, получает прогресс исследования или выполняет квест. Обычный просмотр города не требует участия в игре. Публикация организатора сама по себе не открывает пользователю район.

### UC-08. Организовать и найти марафон

Организатор создаёт спортивную активность, задаёт старт, финиш и полный путь. Пользователь видит линию маршрута и дистанцию, условия регистрации и место сбора; выбирает участие. Подробная постановка — раздел 12.

## 5. Карта, навигация и визуальный язык

### 5.1. Карта

Целевые требования:

- Карта — основной способ обнаружения активности, а не декоративная подложка.
- Различаются запланированное событие, набор участников, сигнал очевидца, квест и маршрутная активность.
- При отдалении точки кластеризуются; выбранная активность не теряется среди маркеров.
- Фильтры: время, интерес/категория, доступность участия, цена; расширенные фильтры открываются отдельно.
- Пустой район, сбой сервера, неработающий картографический ключ и отказ в GPS — разные состояния с разными действиями.
- При выборе марафона карта показывает весь маршрут; общий экран не заполняется линиями всех забегов одновременно.
- Источник данных событий — EventMap. Объекты и организации на карте 2GIS не становятся событиями автоматически.

### 5.2. Игровой стиль без перегрузки

Последние дизайн-ориентиры — «Город-приключение» и «Атлас». Это предпочтения из прототипов, не утверждённая спецификация всех экранов.

- Тематические игровые маркеры: мяч, сцена, телескоп, флаг, маршрут, награда и т. п.
- Системные действия используют единый набор векторных иконок; emoji не заменяют навигацию.
- Форма, цвет и подпись работают вместе: статус нельзя объяснять только цветом.
- Анимация отражает состояние, например новое подтверждение, а не постоянно отвлекает.
- Игровые достижения доступны отдельным слоем; обычному пользователю не обязательно разбираться в XP.
- Читаемые улицы, маршрут, контраст, светлая/тёмная тема и доступность важнее эффектов.
- Ролики остаются видимым входом в реальную активность: от ролика можно перейти к событию и карте.

### 5.3. Навигация — решение для аналитика и дизайнера

Сейчас код главного экрана содержит «Карта / Сейчас / Создать / Квесты / Профиль». Ранняя новая концепция предлагала «Карта / Интерес города / Создать / Мои активности / Профиль».

Предложение: сохранить карту и создание как главные действия; определить единый вход в ролики, интерес города и игровые задания, не добавляя бесконечно вкладки. Марафон создаётся из общего создания, а не требует ещё одной постоянной вкладки. Итоговую информационную архитектуру нужно утвердить на сценариях UC-01–UC-08.

## 6. Создание и жизненный цикл активности

### 6.1. Форма

Целевые шаги: намерение → основная информация → релевантные условия → предпросмотр и публикация. Для марафона добавляется отдельный редактор маршрута.

Общее: название, описание, категория, автор, место, начало/конец и часовой пояс, аудитория, видимость, обложка, необязательный ролик. Дополнительно: лимит мест, правила вступления, цена, возраст/навыки, документ брони, срок жизни сигнала.

У выбранных фото/видео показывается само содержимое, а не только «добавлено». Документы, содержащие личные данные, отделяются от публичной галереи. Загрузка имеет понятные состояния: подготовка, передача, обработка, готовность, ошибка.

### 6.2. Состояния

Предложение для согласования: черновик → проверка, если нужна → опубликовано → идёт → завершено → архив. Отдельные ветви: отклонено, отменено, скрыто модератором, истекло для живого сигнала.

Статус публикации, состояние регистрации и состояние обработки видео — три разные оси. Готовое событие может иметь ещё обрабатываемый ролик. Закрытая регистрация не означает отменённое мероприятие.

### 6.3. Правила

- Сервер повторяет клиентскую валидацию; нельзя обойти её прямым запросом.
- Повтор запроса публикации должен быть безопасным и не создавать копии активности.
- Черновик принадлежит текущему аккаунту; смена пользователя не раскрывает чужую форму.
- Сохранённый текст черновика не означает, что файл из галереи переживёт перезапуск: поведение медиа нужно явно определить.
- При изменении времени, места или маршрута участники видят, что изменилось, и получают уведомление.
- Изменение условий после оплаты требует отдельной политики; сейчас нельзя опираться на mock-покупку как на реальную оплату.
- Удаление, отмена и скрытие различаются: должны сохраняться необходимые связи, история и решения модерации.

## 7. Интерес города и подтверждение происходящего

### 7.1. Что показывать

Растущие темы, активности с интересом рядом, почти собранные группы, подтверждённые находки и спрос по районам. Экран должен объяснять период и источник показателя, например «за последние 24 часа», а не выдавать накопленный счётчик за происходящее сейчас.

### 7.2. Независимые сигналы

Предварительная продуктовая шкала из концепции: 1 очевидец — «замечено», 2 — «подтверждается», 3–4 — «происходит сейчас», 5+ — «городской импульс». Порог — гипотеза, а не гарантия достоверности или безопасности.

Аналитик должен определить георадиус, временное окно, категории, признаки совпадения, срок актуальности и возможность отмены ошибочного объединения. Один автор не должен считаться несколькими очевидцами; рекламные публикации автора не равны независимым подтверждениям.

Текущий поиск похожего сигнала использует географический прямоугольник, категорию и близость нормализованного названия. Это не полноценный алгоритм с заявленными в старой документации метрами и временным окном. Повторная публикация сейчас может вызвать toggle подтверждения и снять прежнюю отметку — требуется идемпотентная семантика.

### 7.3. Пассивная плотность и явные подтверждения

Существующий PulseService агрегирует геопинги. Это отдельный источник, не доказательство того, что люди увидели одну и ту же активность. Нельзя заменить требуемые «2–5 очевидцев подтвердили» числом устройств рядом.

Перед выпуском нужны: согласие на сбор, ограниченный срок хранения, серверные правила доступа и порог обезличенного показа. Сырые перемещения не должны попадать на общую карту. Запрещено строить карту местоположений несовершеннолетних или использовать её для поиска детей поблизости.

## 8. Фото, ролики и лента

Целевая модель: медиа принадлежит активности, имеет автора, тип, время создания/загрузки, состояние обработки, видимость и статус модерации. Метка «с места» требует отдельного основания; сама загрузка файла не доказывает присутствие.

Ролики нужны для понимания атмосферы, а не для потери связи с картой. В плеере видны активность, место, актуальность и переход к участию. Контент автора отделён от участнического.

В коде подготовлен Mux: прямая передача файла, асинхронная обработка, подписанное воспроизведение и обработчик уведомлений провайдера. Фото и старые ролики остаются в прежнем storage. На дату последней проверки Mux не был включён на рабочем сервере; реальная загрузка и проигрывание через него не подтверждены.

Важно для постановок:

- Не называть короткий загруженный ролик прямой трансляцией. Полноценный livestream — отдельный сценарий, не подтверждён текущей интеграцией.
- Решить, относятся комментарии к Event или отдельному ролику: текущий основной контур комментариев привязан к Event.
- Показать обработку, ошибку формата, отсутствие доступа, истёкшую ссылку и повтор.
- Не хранить ключи провайдера в приложении; не пересылать авторизационный токен EventMap на upload-домен.
- Подписанные видео не делают старые публичные фото и документы приватными задним числом.
- Запланировать удаление брошенных загрузок, лимиты расходов, модерацию, жалобы и отзыв доступа.
- Текущая загрузка — один PUT в открытом приложении с файлом в памяти; фоновое возобновление не реализовано.

## 9. Участие, друзья, приглашения и уведомления

### 9.1. Участие

Нужна единая модель: не участвую / ожидаю / одобрен / отказано / отменил / посетил. Для марафона дополнительно может быть регистрация на конкретную дистанцию и отдельный результат.

Лимит должен проверяться на сервере атомарно: если осталось одно место, два одновременных запроса не получают оба подтверждение. Нужно определить, занимают ли место ожидающие заявки, гости приглашения и неоплаченные бронирования. Установить правила повторной заявки и отмены.

Сейчас существуют отдельно attendance и заявки на вступление; их требуется согласовать. Число друзей среди «идущих» не равно «друзья уже на месте».

### 9.2. Социальные функции

Друзья, подписки на организаторов, приглашения и ответы гостей имеют серверные заготовки/реализации. Персональная геолокация друзей должна включаться добровольно, иметь срок актуальности и немедленное отключение. Её нельзя смешивать с обезличенным городским интересом.

Чаты в текущем проекте представлены sample-интерфейсом, не готовой перепиской. Если чат нужен для команды, марафона или гостей свадьбы, это отдельный эпик с хранением, доставкой, блокировками и модерацией.

### 9.3. Уведомления

Разделить три канала:

1. Внутренняя лента уведомлений — серверные записи в приложении.
2. Локальное напоминание — планируется на устройстве, сейчас предусмотрено «за час до начала».
3. Удалённый push — доставка через внешний сервис, требует серверной и клиентской настройки.

В коде есть FCM-отправитель, но полноценная мобильная регистрация и фактическая доставка не подтверждены. Актуальный серверный маршрут регистрации устройства — `/push/register`; старое описание `/push/token` в `PUSH_SETUP.md` расходится с кодом.

Для марафонов нужны уведомления о подтверждении регистрации, изменении старта/маршрута, отмене и приближении начала. При смене времени пересчитывается напоминание. Отсутствие разрешения на уведомления показывается честно; Android WorkManager не является гарантией срабатывания в точную секунду.

## 10. Игровой город и квесты

### 10.1. Исследование города

Целевое требование владельца: город постепенно открывается личным посещением. Туман относится прежде всего к исследованию и участническим открытиям, а не скрывает всю полезную афишу.

Предлагаемые правила:

- Публичный концерт или марафон можно найти до посещения района.
- Закрытая активность не становится публичной после «открытия» района.
- Личное открытие района не равно разрешению показать свою геопозицию другим.
- Ролики/находки могут открываться по правилам игрового слоя; ограничения должны объясняться.
- Награда выдаётся сервером один раз за проверяемое действие; предусмотрена защита от повторов.
- Никаких наград за посещение опасных, закрытых или недоступных территорий.

### 10.2. Квесты аккредитованных организаций

В коде: только одобренный бизнес создаёт квест, от 1 до 10 точек, условия geo/photo/purchase; квест проходит модерацию. Есть последовательность точек, прохождение, XP и призовой сценарий.

Необходимо доработать проверку доказательств и злоупотреблений. Например, текущий purchase-код вычисляется по ID точки: комментарий «одноразовый QR с чека» не доказывает, что код уникален для каждой покупки. Аналитик должен описать выпуск, срок действия, погашение и запрет повторного использования.

Марафон не следует автоматически превращать в промоквест с обязательными покупками. Общими могут быть точки и проверка посещения, но условия участия, спортивный результат и коммерческие награды различаются.

XP, уровни, миссии, районы, лидерборды и капсулы представлены разной степенью реализации. Сезонный пропуск, premium и часть показателей — прототипы; не считать монетизацию готовой.

## 11. Организации, аккредитация и администрирование

### 11.1. Аккредитация

Текущий процесс в коде: пользователь подаёт БИН/ИИН, юридическое и публичное название, категорию, контакты и документы → `pending` → администратор одобряет или отклоняет → повторная подача после отказа.

Сейчас проверка номера — формат из 12 цифр, не подтверждение существования организации в реестре. Аккредитация означает проверенные сведения, а не абсолютную безопасность организатора или мероприятия.

Целевая постановка должна добавить:

- Проверку связи представителя с организацией и право действовать от её имени.
- Различие бизнеса, сообщества, спортивного клуба и государственного учреждения.
- Причины отказа, запрос дополнительных сведений, приостановку/отзыв и повторную проверку.
- Защищённое хранение документов и ограничение доступа к ним.
- Роли нескольких сотрудников, историю решений и уведомление заявителя.
- Привязку события к организации отдельно от пользователя, который нажал «опубликовать».

### 11.2. Админка

Есть HTML-страница `/admin` внутри backend, очереди бизнеса и квестов, решения через `X-Admin-Key`. Это техническая мини-админка, не полноценная система сотрудников.

Целевой состав: организации и документы; события и маршруты; жалобы; фото/ролики; пользователи и ограничения; квесты/награды; справочники; журнал действий. Полномочия проверяются сервером, а не только скрытием кнопок.

### 11.3. Безопасность пользователей

Жалоба должна сохраняться на сервере и доходить до очереди модератора. Сейчас основной экран жалобы переключается в локальное состояние «отправлено» без серверной отправки — это незавершённый защитный сценарий.

Нельзя допускать частные объявления, привлекающие исключительно детей, поиск детей рядом и публичную геолокацию несовершеннолетних. Семейные мероприятия должны ясно описывать сопровождение и организатора. Возрастные правила, обработка документов, ответственности и требования к массовым мероприятиям подлежат отдельной профильной проверке перед выпуском; этот документ не заменяет её.

## 12. Марафоны и маршруты — новая постановка

### 12.1. Запрос и границы

**Подтверждённое требование владельца:** пользователь/организатор создаёт марафон; другим видно, откуда и куда он проходит.

Для первой версии под марафоном здесь понимается физический забег по маршруту в городе. Общая модель может позже поддержать велозаезд, прогулку или поход. Онлайн-марафон привычек на 30 дней — другой сценарий и в эту постановку не входит.

Основной результат: не две несвязанные метки, а **старт + финиш + линия полного пути + направление + дистанция + условия участия**. Слова «марафон» и «забег» не должны заставлять систему считать любую длину одинаковой: отображается фактически заданная дистанция.

Все детали ниже — предлагаемая спецификация для уточнения аналитиком. В текущем коде отдельной сущности марафона и редактора его трассы не обнаружено.

### 12.2. Кто создаёт

- Обычный пользователь — любительский забег/совместную пробежку без знака официальной организации.
- Проверенная организация — мероприятие от своего имени с проверенным источником.
- Массовое, платное или семейное мероприятие может требовать дополнительной модерации по утверждённым правилам риска.
- Нельзя выдавать одобрение публикации на платформе за разрешение на перекрытие улиц или гарантию безопасности трассы.

Конкретные пороги и документы для массового мероприятия — открытое решение владельца и профильных специалистов, а не выдуманный числовой лимит.

### 12.3. Создание: пошаговый сценарий

1. Нажать «Создать» → «Я организую» или «Ищу людей» → формат «Забег / марафон».
2. Указать название, описание, автора и обложку; ролик необязателен.
3. Указать дату, время сбора, время старта, ожидаемое окончание и часовой пояс.
4. Выбрать точку старта на карте или через поиск места; подтвердить адрес/ориентир.
5. Выбрать точку финиша. Для кругового маршрута разрешить совпадение старта и финиша.
6. Добавить промежуточные точки и сформировать весь путь, по которому реально планируется движение.
7. Проверить направление, длину, число кругов при необходимости, описание покрытия/условий. Если геометрии нет, две точки не выдаются за готовую трассу.
8. Задать участие: бесплатно/платно, лимит, открытая регистрация/одобрение/приглашение, срок регистрации, возраст и подготовка.
9. Добавить организационные сведения: место сбора, контакт, правила отмены, вода/помощь, ограничения и документы при необходимости.
10. Увидеть предпросмотр карточки и всей трассы, сохранить черновик или опубликовать/отправить на модерацию.

Редактор сложного маршрута не обязан укладываться в цель «создание за 60 секунд», относящуюся к простой активности.

### 12.4. Обязательные и дополнительные данные

| Данные | Первая версия | Примечание |
| --- | --- | --- |
| Event и автор | Обязательно | Использовать общие права и жизненный цикл |
| Название, описание, формат | Обязательно | Понятно, соревнование это или совместная пробежка |
| Начало и часовой пояс | Обязательно | Время сбора отдельно от старта |
| Старт | Обязательно | Координаты, название/ориентир |
| Финиш | Обязательно | Может совпадать со стартом |
| Геометрия маршрута | Обязательно для публикации как маршрутной активности | Упорядоченная линия, а не расстояние по прямой |
| Длина | Обязательно | Вычисляется из геометрии; заявленная организатором длина хранится отдельно при необходимости |
| Направление и круги | Для соответствующего маршрута | Круговой маршрут не имеет нулевую длину |
| Условия регистрации | Обязательно | Правило вступления, срок, ограничения, цена, лимит либо явно «без лимита» |
| Видимость | Обязательно | Публичная/по ссылке/по приглашению |
| Версия маршрута | Обязательно технически | Для изменений и уведомления участников |
| Контрольные точки | Необязательно на первом этапе | Порядок, тип, место, название; не означают автоматический спортивный зачёт |
| Пункты воды, помощи, встречи | Необязательно | Отдельные типы точек, не все являются обязательными для прохождения |
| Контакт и правила | Обязательно по согласованной политике | Личный телефон не обязан быть публичным |

| GPS-трек и время участника | Не входят в первый этап | Требуют отдельного согласия, хранения, фоновой работы и антифрода |

### 12.5. Редактор маршрута и 2GIS

Предлагаемый минимум: выбор старта/финиша и промежуточных вершин, перетаскивание/удаление точки, отмена последнего действия, предпросмотр целиком и сохранение геометрии. Ручной путь должен явно называться «маршрут организатора», а не проверенный безопасный маршрут.

Автопостроение по дорогам — отдельная интеграция. Наличие SDK карты 2GIS не доказывает доступ к поиску, маршрутизации или нужному режиму движения. До разработки нужно проверить договорённости и технические возможности выбранного сервиса. Не обещать прокладку пешеходного маршрута автоматически только из факта отображения карты.

GPX/GeoJSON-импорт — возможное расширение. При включении потребуются ограничения размера, точек и длины, обработка разрывов и повреждённых файлов. Для первой версии импорт необязателен.

Геометрия хранится независимо от конкретного SDK. Если выбирается GeoJSON, порядок координат — `[longitude, latitude]`; в текущих DTO проекта отдельные поля `lat/lng`. Преобразование фиксируется и тестируется, иначе маршрут окажется не в том городе.

Отдельные понятия:

- **Трасса мероприятия** — путь, выбранный организатором.
- **Как добраться до старта** — персональный маршрут пользователя к месту сбора; не изменяет трассу.
- **Трек участника** — фактически пройденный путь; не создаётся автоматически из первых двух.

### 12.6. Просмотр и участие

На общей карте марафон имеет специальный маркер. После выбора открывается линия трассы и карточка; камера охватывает маршрут с отступами под элементы интерфейса. Старт/финиш различаются иконкой и подписью, направление — стрелками или иным понятным обозначением.

Карточка содержит: название, организатора и статус источника, дату, время сбора/старта, длину, карту, условия и стоимость, число зарегистрированных/свободных мест, ограничения, действия «Интересно», «Участвовать» и «Как добраться до старта».

Роли зрителя и бегуна не смешиваются: интерес к мероприятию не занимает стартовое место. В первой версии можно ограничиться одним типом регистрации участника, но не считать всех зрителей зарегистрированными бегунами.

При выборе дистанции регистрация должна ссылаться именно на неё. На первом этапе допускается одна дистанция; при расширении пользователь не должен попадать сразу на все дистанции одного мероприятия.

### 12.7. Изменения и отмена

- До публикации автор свободно редактирует черновик.
- После регистрации первого участника существенное изменение старта, финиша, длины, времени или правил создаёт новую версию и уведомляет участников.
- Старую версию не перезаписывать бесследно: хранить историю и причину.
- Определить, какие изменения требуют повторного согласия и повторной модерации.
- После начала запрещать тихую замену трассы; экстренное изменение выделяется явно.
- Отмена закрывает регистрацию, отменяет напоминания и объясняет следующий шаг. Для реальной оплаты нужна согласованная политика возврата.
- Две одновременные правки не должны молча затирать друг друга; предусмотреть проверку версии.

### 12.8. Отслеживание и спортивный результат

Первый этап **не требует непрерывного GPS-слежения**. Достаточно опубликованного пути, регистрации и при необходимости отметки у старта/финиша с понятным уровнем доверия.

Кнопка «Я финишировал» может быть только самоотчётом; её нельзя выдавать за подтверждённый официальный результат. Официальный хронометраж, чипы, доказательство прохождения и защита от подмены GPS — отдельная интеграция/постановка.

Если позднее добавляется трекинг: добровольное включение, выбранные зрители, остановка по запросу, индикатор актуальности, понятный срок хранения, удаление данных, работа при пропаже сети и ограничение фонового расхода батареи. Местоположения всех бегунов не становятся публичными по умолчанию.

### 12.9. Приватность и безопасность

Закрытый забег не раскрывает постороннему ни старт, ни финиш, ни линию, ни список участников. Проверка нужна для карточки, выдачи карты, медиа, прямых ссылок и уведомлений. Игровое «открытие района» не обходит эти права.

Показ трассы не означает, что платформа проверила доступность территории. Участник должен видеть источник маршрута и сообщать об опасной/недоступной точке. Маршрут нельзя автоматически объявлять разрешённым для массового мероприятия.

### 12.11. Критерии приёмки первой версии

- **MAR-01:** автор создаёт забег с валидными стартом, финишем и линией; другой пользователь открывает те же данные после перезапуска приложения.
- **MAR-02:** старт, финиш, промежуточные точки и направление понятно отображаются на карте; маршрут не смещается при масштабе/вращении.
- **MAR-03:** круговой маршрут со совпадающими стартом/финишем сохраняется с ненулевой длиной и корректным числом кругов.
- **MAR-04:** сервер отклоняет нечисловые/недопустимые координаты, пустую или вырожденную геометрию, несогласованные старт/финиш и некорректное время; численные допуски согласованы и покрыты тестами.
- **MAR-05:** длина считается по пути, а не по прямой между концами; единицы и правила округления одинаковы на клиенте и сервере.
- **MAR-06:** выбор точек без готового пути не публикуется как полноценная трасса; сбой построения объясняется пользователю.
- **MAR-07:** одновременные регистрации не превышают лимит, повтор одной заявки не занимает второе место.
- **MAR-08:** закрытый маршрут недоступен постороннему даже по известному ID; открытие района не даёт доступ.
- **MAR-09:** изменение опубликованной трассы создаёт версию; участник видит изменения, уведомление не дублируется при повторной обработке.
- **MAR-10:** отмена закрывает набор, корректно обновляет карту и напоминание; повторная отмена безопасна.
- **MAR-11:** при отказе в GPS маршрут можно посмотреть и выбрать место вручную; приложение не требует фоновой геолокации только для просмотра.
- **MAR-12:** при потере сети черновик не теряется, ошибка не превращается в ложный успех; повтор публикации не создаёт второй забег.
- **MAR-13:** фото и ролик открываются из карточки именно этого забега; обрабатываемое видео не блокирует просмотр маршрута.
- **MAR-14:** «Как добраться до старта» не подменяет и не редактирует трассу организатора.
- **MAR-15:** неподтверждённый самоотчёт о финише не отображается как официальный результат.

### 12.12. Рекомендуемое дробление

**М1:** одна дистанция, ручной маршрут, старт/финиш, карточка, черновик, публикация, базовое участие и доступ. Это минимальное выполнение запроса владельца.

**М2:** несколько дистанций, импорт, контрольные точки, версии с повторным согласием, инструменты организатора и более подробные уведомления.

**М3:** live-трекинг по согласию, результаты, внешняя система хронометража, командные зачёты. Только отдельным решением, не скрытой частью М1.

## 14. Критические пробелы, которые нельзя скрывать от команды

1. **Приватность карточки.** `GET /events/{id}` публичный и вызывает чтение по ID без проверки зрителя. Скрытие из списка карты не защищает прямую ссылку. Требуется единая серверная политика для карточек, участников, комментариев, медиа и маршрутов.
2. **Лимиты и единая регистрация.** `requestJoin` и `reviewJoin` записывают статус без проверки capacity. Attendance живёт отдельно. Нельзя обещать бронирование последнего места.
3. **Достоверность подтверждения.** `confirm` переключается без геодоказательства и исключения автора. Повторы объединения сигналов могут снимать подтверждение.
4. **Честные цифры.** `withLiveCounts()` прибавляет attendance к сохранённым goingCount/liveViewers; учитывает строки attendance без разделения «иду/был». Это не корректный учёт зрителей онлайн и участников по состоянию.
5. **Моки в пользовательском потоке.** Каталог квестов может заменять пустой ответ sample-данными; есть локальный демо-успех чек-ина. Demo допустимо только в явно выделенном режиме.
6. **Жалобы и блокировки.** Нужен работающий путь до модератора, а не только экран успеха.
7. **Медиа и приватные документы.** Защита новых Mux-видео не закрывает публичные URL старых файлов. Доступ и удаление должны быть последовательны.
8. **Внешние сервисы.** Код адаптера не означает подключённые 2GIS, Mux, FCM или платёжную систему. Нужны владельцы аккаунтов, окружения, секреты и реальные проверки.
9. **Истечение и время.** Поле expiresAt не гарантирует исчезновение во всех выдачах. Поиск карты сейчас не фильтрует его явно. Нужны единые правила актуальности.
10. **Готовность платформ.** Успешный Android APK не означает готовность iOS; наличие common-кода не заменяет нативные реализации.
11. **Разъехавшаяся документация.** В старых файлах встречаются другие карты, хранилища, обещания WebSocket/офлайн-очереди и «полный паритет». Их нельзя использовать как отчёт о фактической готовности.

Это перечень обнаруженных рисков, а не полный аудит безопасности всего приложения.

### 16.1. Зафиксированные проверки

В `MUX_VIDEO.md` за 05.11.2026 отмечены: 33 backend-теста в запуске с локальной симуляцией, 22 теста выбранных мобильных JVM-модулей и успешный Android assembleDebug. Перенос Mapbox-токена в локальную конфигурацию также прошёл Android-сборку.

iOS-компиляция тогда не завершилась из-за нехватки места. Реальные Mux upload/HLS, применение V14 в рабочем PostgreSQL и устройство с ключом 2GIS не были проверены. Это не регрессионная сертификация всего продукта.

### 16.2. Общий Definition of Done для функции

- Понятны роль, цель, вход, результат, ошибки, права и зависимости.
- Мобильный сценарий выполняется с настоящим backend; пустые/ошибочные ответы не маскируются sample-успехом.
- Состояние сохраняется и читается заново после перезапуска/обновления экрана.
- Сервер проверяет доступ к каждому объекту, включая прямой ID и медиа.
- Повторы запросов, конкурентные изменения и потеря сети не создают дубликаты/переполнение.
- Есть контрактные, модульные и сценарные проверки в нужном объёме; для геофункции — проверка на устройстве.
- Документация и миграции соответствуют реализованному поведению.
- Уведомления, аналитика, логирование ошибок и возможность поддержки определены.
- Для каждой платформы отдельно указано: поддержано, ограничено или не поддержано.

### 16.3. Нефункциональные требования к согласованию

Производительность измерять на согласованных устройствах, сети и размере набора событий: время открытия карты, карточки и маршрута, задержка поиска, загрузка/обработка медиа, отзывчивость при перемещении карты. Значения не придумывать постфактум — согласовать бюджет и стенд.

Обязательные классы проверок: отказ/потеря GPS, нет интернета, просроченная сессия, смена аккаунта, нехватка места, большой файл, сворачивание, изменение часового пояса, отозванное приглашение, несколько одновременных регистраций, недоступность внешнего провайдера.

Ограничения хранения: сроки для геопингов, маршрутов, приглашений, документов, медиа, жалоб и истории решений должны иметь владельца и обоснование. Логи не должны содержать пароли, токены, upload URL и точные маршруты пользователей без необходимости.

### 16.4. Продуктовая аналитика

Предлагаемые события измерения: карта открыта; активность открыта; интерес включён; заявка подана/одобрена/отменена; публикация начата/завершена/ошиблась; ролик загружен/готов; маршрут открыт; регистрация на забег завершена; изменение маршрута прочитано; жалоба зарегистрирована/решена.

Каждое событие аналитики должно иметь определение, источник, дедупликацию и разрешённые свойства. Не отправлять сырой GPS-трек и документы в общую продуктовую аналитику. Отдельно измерять подтверждённое участие и самоотчёт.

## 17. Порядок реализации

Порядок — рекомендация на основании найденных зависимостей, без неподтверждённых календарных обещаний.

### Этап А. Зафиксировать продукт и устранить опасную незавершённость

Утвердить словарь, игровое направление и навигацию; убрать ложные успехи; закрыть доступ к приватным данным; согласовать участие/attendance; проверить capacity; реализовать рабочие жалобы; определить смысл счётчиков и подтверждений.

Критерий выхода: можно честно показать «создал → другой увидел → присоединился → автор видит участника», а закрытую активность не получает посторонний.

### Этап Б. Довести карту и медиа

Получить и проверить 2GIS для целевых платформ; принять единую систему маркеров и карточек; подключить настоящий видеосервис; настроить уведомления; проверить ошибки и работу на устройстве.

Критерий выхода: карта читаема, данные реальны, ролик конкретной активности загружается и воспроизводится, отсутствие доступа/сети объясняется.

### Этап В. Марафоны М1

После согласования модели участия и прав: данные маршрута, редактор, старт/финиш/линия, карточка, регистрация и контроль изменения. Сначала одна дистанция. Принять по MAR-01–MAR-15 в применимой части.

Проектирование маршрута и UX можно вести параллельно этапам А/Б; выпускать поверх известных дыр приватности и лимитов нельзя.

### Этап Г. Живой и игровой город

Надёжные независимые подтверждения, объединение и истечение сигналов; исследование районов; квесты с доказательствами и честными наградами; отсутствие демо-данных в production-потоках.

### Этап Д. Расширения после пилота

Марафоны М2/М3, команды организаций, полноценная админка, реальная оплата, чат, расширенная статистика и монетизация. Приоритет уточняется результатами пилота, а не количеством уже нарисованных экранов.

## 18. Что должен подготовить аналитик

### 18.1. Артефакты на выходе

1. **Краткий PRD:** ценность, аудитория, границы релиза, гипотезы и метрики.
2. **Словарь и модель домена:** Event/Activity, тип/формат/источник, участие, подтверждение, маршрут и версии.
3. **Матрица ролей и доступа:** объект, операция, роль, видимость, основание доступа, отзыв.
4. **Use cases / user stories:** основной, альтернативный и ошибочный поток для UC-01–UC-08.
5. **Состояния и переходы:** активность, заявка, медиа, аккредитация, квест, маршрут, регистрация на забег.
6. **Реестр экранов:** входы, действия, состояния загрузки/ошибки/пустоты, доступность, соответствие Android/iOS.
7. **Системные постановки:** изменения данных, API и событий, миграции, совместимость и интеграции. OpenAPI/Swagger — отдельно по фактическому и целевому контракту, без смешения.
8. **Backlog с зависимостями:** приоритет, ответственный, внешние блокеры, критерии приёмки и способ проверки.
9. **План приёмки:** тесты приватности, конкурентности, геометрии, мультимедиа и реальных устройств.
10. **Реестр решений:** что согласовано владельцем, что предложено, что отложено и почему.

### 18.2. Шаблон одной постановки

Идентификатор и название → цель/проблема → роль → предусловия → основной поток → альтернативы и ошибки → поля и проверки → права → состояния → зависимости → критерии приёмки → аналитика → миграция/совместимость → открытые вопросы.

Каждый экран должен ссылаться на сценарий, каждый API-метод — на потребителя и правило доступа, каждый критерий — на проверку. Скриншот или список endpoints не заменяет бизнес-правила.

### 18.3. Решения, которые нужно вынести владельцу

- Какие сценарии входят в ближайший пилот: базовая карта, игровой слой, ролики, квесты, марафоны?
- Как совместить «Интерес города», «Сейчас» и «Мои активности» без перегруза навигации?
- Можно ли обычному пользователю публиковать большой открытый забег и когда нужна модерация?
- Первая версия марафона — одна дистанция или сразу несколько; ручная линия или обязательное автопостроение?
- Нужна ли фактическая регистрация бегунов в первом релизе или лишь объявление и переход на внешний сайт? В этом документе предложена внутренняя базовая регистрация.
- Кто считается участником, когда занято место и как связаны заявка, attendance, билет и RSVP?
- Что считается существенным изменением маршрута; когда требуется повторное согласие?
- Какие документы проверяются для организаций и массовых мероприятий, кто имеет к ним доступ?
- Каким способом подтверждается присутствие и как защищаться от накрутки?
- Какие функции доступны несовершеннолетним и как проверяется сопровождение?
- Нужны ли публичные результаты забегов и live-трекинг? По умолчанию в М1 их нет.
- Кто владеет аккаунтами 2GIS/Mux/FCM/storage и бюджетами, кто принимает эксплуатационные решения?
- Какие языки, города и платформы обязательны для первого запуска?

### 18.4. Критерий хорошей аналитики

После работы аналитика другой разработчик должен понять без устного пересказа: что строится, для кого, что уже можно переиспользовать, что является прототипом, как проверять права, какие ошибки показывать и по какому тесту принимать результат. Нельзя завершить работу формулировкой «сделать как в макете».
