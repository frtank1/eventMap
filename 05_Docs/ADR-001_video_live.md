Статус: **предложено** (ревью к 14.06.2026) · PM-решение по 4 открытым вопросам из `API_CONTRACT.md`.

## Вопрос 1 (главный): транскод и раздача LIVE — свои силы или провайдер?

### Варианты

**A. Свой стек (R2 + ffmpeg + HLS).** Принимаем RTMP/WebRTC на свой сервер, режем на HLS своим ffmpeg, кладём сегменты в R2, отдаём через CDN.
- ➖ Реалтайм-транскод 1080p, авто-масштабирование под пики, ABR-лестница, плеер, DVR — это месяцы работы и постоянная эксплуатация. Для команды 1–2 человека неподъёмно к срокам.
- ➕ Нет per-minute платы провайдеру.

**B. Cloudflare Stream.** Live + VOD «под ключ»: ingest (RTMP/WebRTC/SRT), авто-транскод, ABR, авто-запись в VOD, плеер/HLS — из коробки.
- Цены (2026): ingest **бесплатно**, доставка **$1 / 1000 мин просмотра** ($0.001/мин), хранение записей **$5 / 1000 мин** ($0.005/мин/мес). Эфир без зрителей — $0 доставки.
- ➕ Уже в экосистеме Cloudflare (у нас R2) — один вендор, один биллинг.
- ➕ Bandwidth включён, без egress-сюрпризов.

**C. Mux.** Премиальный DX и аналитика.
- Цены (2026): encoding **$0.07/мин**, доставка **$0.025/мин** (live), что в разы дороже Cloudflare на доставке.
- ➖ Дороже, отдельный вендор.

### Решение: **B — Cloudflare Stream** для LIVE и видео-VOD.
Короткие видео ≤30 сек (E3/E4, не-live) — тоже через Stream (VOD upload), фото — остаются в **R2**. Mux держим как план Б, если упрёмся в фичи аналитики.

### Прикидка стоимости (сценарий: 1000 LIVE-минут эфира/мес, в среднем 50 зрителей, записи хранятся месяц)
- доставка: 1000 мин × 50 зрителей × $0.001 = **$50**
- хранение записей: 1000 мин × $0.005 = **$5/мес** (накопительно)
- ingest: $0
- → порядок **$55/мес** на старте; масштабируется линейно от просмотров. Под бету бюджет приемлемый.

### Влияние на API-контракт
- `POST /media/upload-url` → для фото отдаёт presigned R2; для видео — создаёт Stream upload (direct creator upload URL).
- LIVE: `POST /events/{id}/live/start` отдаёт Stream Live Input (RTMP key + playback URL); WS-событие `event_live` несёт `playbackUrl` (HLS).
- Вебхук Cloudflare Stream → наш бэкенд: `video.ready`, `live_input.connected/disconnected` → обновляем `status` и шлём WS/push.

## Вопрос 2: расчёт статуса события (soon → live → ended)

Гибрид:
- Базово — **вычисление на лету** из `start_at/end_at` в гео-запросе (событие «soon» до старта, «ended» после end_at).
- Флаг **`live`** ставится фактом эфира: вебхук `live_input.connected` от Stream → `events.status='live'`, `disconnected` → обратно. Не привязываемся только к расписанию, т.к. организатор может начать раньше/позже.
- Фоновая джоба (раз в минуту) подчищает «завис­шие» live по `end_at + grace 30 мин`.
- Никакого тяжёлого крона на каждую запись — статус для карты считается в SQL-запросе bbox.

## Вопрос 3: гео-приватность Sharing «сейчас здесь»

- Точка `sharing_point` живёт с **TTL 2 часа** (`sharing_updated_at`); по истечении — не отдаётся, фон-джоба обнуляет.
- Видимость — настройка пользователя (H11/I2): `nobody | subscribers | mutual`. По умолчанию **subscribers**.
- Координаты огрубляются до **~50–100 м** на выдаче (не показываем точный адрес).
- Полное отключение — мастер-тумблер, мгновенно скрывает пин.
- Гео-точность пользователя на устройстве — «при использовании», без фонового трекинга (как обещано на экране B1).

## Вопрос 4: rate limit и анти-спам

- Глобальный лимит на IP/токен на gateway (Ktor): напр. 100 req/мин.
- Чувствительные ручки:
  - `/media/upload-url` — 20/час на пользователя (анти-флуд загрузок).
  - `/reports` — 10/сутки на пользователя + дедуп по `(reporter_id,target_id)`.
  - `/auth/*` — 5 попыток/15 мин на email+IP, экспоненциальный backoff.
- 429 + заголовок `Retry-After`. Хранилище счётчиков — Redis (добавляем в стек) либо Postgres-таблица на MVP.
