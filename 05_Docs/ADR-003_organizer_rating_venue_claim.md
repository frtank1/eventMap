# ADR-003 — Рейтинг организатора и верификация локаций (venue claim)

Статус: **принято** · 02.06.2026. Две связанные фичи поверх ADR-002.

Контекст: в ADR-002 оценка ставится на ивент, а `organizer_avg_rating` — это просто среднее по ивентам, которое идёт в формулу важности пина. Здесь мы (1) делаем организатора полноценной рейтинговой сущностью с историей и общим баллом, и (2) даём организациям заявить свою площадку, чтобы чужие ивенты на их точке проходили через подтверждение.

---

## Фича 1. Рейтинг организатора

### Принцип
Оценку по-прежнему ставит пользователь **на ивент** (как в ADR-002): после `end_at`, только подтверждённый `was`, 1–5, одна на юзера, правка 7 дней. Новое — что происходит с этой оценкой дальше:

```
оценка ивента → агрегат ивента (rating_avg) → после завершения «оседает» в историю организатора
   → у организатора: список прошедших ивентов с их рейтингами (история)
   → общий рейтинг организатора = взвешенное среднее по всем завершённым ивентам
```

То есть отдельной «оценки организатора напрямую» нет — это защищает от накрутки (оценивать можно только то, на чём ты реально был). Рейтинг организатора целиком производный, но представлен как самостоятельная сущность: профиль, история, общий балл.

### Формула общего рейтинга организатора

```
organizer_rating =
    Σ (event.rating_avg * event.rating_count) / Σ (event.rating_count)   // по завершённым ивентам

confidence  = min(1, total_rating_count / 30)        // мало отзывов → показываем «новичок»
display     = organizer_rating, если confidence >= порог; иначе бейдж «недостаточно оценок»
```

Опционально (на будущее, отдельным флагом) — **recency-вес**: ивенты последних 6 мес весят больше, чтобы рейтинг отражал актуальное качество, а не давние заслуги:

```
weight(event) = event.rating_count * decay(months_since_end)
decay(m)      = 0.5 ^ (m / 6)        // период полураспада 6 мес
```

### Связь с важностью пина (ADR-002)
В формуле importance компонент `20 * (organizer_avg_rating / 5)` теперь читает `organizers.rating` (этот общий рейтинг) вместо пересчёта на лету. Поведение совместимо, источник — одно поле.

### Экраны
- **H8 (профиль организатора)**: блок «★ 4.6 · 128 оценок · 23 ивента», переключатель **История ивентов** со списком прошедших событий и их рейтингами.
- **D1 (карточка ивента)**: рядом с рейтингом ивента — мини-бейдж организатора со ссылкой на H8.
- **P4** (оценка ивента) — без изменений, остаётся точкой входа.

## Фича 2. Верификация локаций (venue claim & confirm)

### Проблема
Организация имеет физический адрес/площадку (кафе, коворкинг, клуб, студия). Кто-то создаёт ивент с пином на этой точке — возможно без ведома владельца. Владелец должен это **видеть** и **подтвердить или отклонить**. Не касается общественных мест (парки, площади, улицы).

### Модель
1. Организация заявляет одну или несколько площадок: `venues` с координатами, радиусом (`claim_radius`, по умолчанию 50 м) и пруфом владения (документ/договор аренды → ручная верификация модератором, как в `CATEGORIES_AND_ROLES` §4.5).
2. При создании ивента бэкенд проверяет пин:
   - **Гео-чек по реестру публичных зон** (PostGIS-слой `public_zones` из OSM + ручной реестр: парки, скверы, площади, набережные, пешеходные улицы — для пилота в Астане это зона Нур-Жол/Байтерек, набережная Ишима, парк Президента и т.п.). Пин внутри публичной зоны → подтверждение **не требуется**, ивент публикуется как обычно.
   - Иначе ищем заявленные `venues`, чей `claim_radius` накрывает пин.
3. Если пин попал в чью-то заявленную площадку и создатель ивента — **не** владелец этой площадки:
   - ивент создаётся со статусом `venue_status = 'pending'` и **скрыт с карты** до подтверждения (выбор: скрыт до подтверждения);
   - владельцу площадки — пуш + запись в очередь «Подтверждения площадки»;
   - владелец **подтверждает** → ивент публикуется обычным путём (дальше авто-модерация), либо **отклоняет** → ивент уходит в **очередь модерации** (не удаляется автоматически), создатель уведомлён;
   - **тайм-аут 48 ч** без реакции владельца → авто-эскалация в очередь модерации (не авто-публикация и не авто-удаление — решает человек).
4. Если создатель ивента сам владелец площадки → `venue_status = 'self'`, подтверждение не нужно.

### Краевые случаи
- Точка попадает и в публичную зону, и в радиус площадки → приоритет у площадки (частное важнее), требуется подтверждение. Исключение: явно «уличный» формат (категория 1.10) на публичной улице — настраивается флагом.
- Несколько площадок накрывают пин → уведомляются все владельцы, достаточно подтверждения одного (того, чей центр ближе), остальным — инфо.
- Антиспам: владелец не может «захватить» гигантский радиус — `claim_radius` ограничен (например ≤ 150 м) и проверяется модератором при верификации площадки.

## Дельта API (`API_CONTRACT.md`)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/organizers/{id}/rating` | общий рейтинг + confidence + история ивентов с оценками |
| POST | `/venues` | заявить площадку (координаты, радиус, пруф) → на верификацию |
| GET | `/venues/mine` | мои площадки и их статусы |
| GET | `/venues/{id}/pending-events` | чужие ивенты, ожидающие подтверждения на моей площадке |
| POST | `/venues/{id}/events/{eventId}/confirm` | подтвердить чужой ивент |
| POST | `/venues/{id}/events/{eventId}/reject` | отклонить → в очередь модерации |
| GET | `/geo/venue-check?lat=&lng=` | вернуть: публичная зона? / заявленная площадка? (для шага создания) |

`GET /events` — в ответ добавляется `venueStatus` (`none|self|pending|confirmed|rejected`). Ивенты с `pending`/`rejected` **не отдаются** в гео-выдаче карты.

## Дельта схемы БД

```sql
-- Организатор как рейтинговая сущность
ALTER TABLE organizers
  ADD COLUMN rating        REAL DEFAULT 0,   -- общий рейтинг, пересчёт фоновой джобой
  ADD COLUMN rating_count  INT  DEFAULT 0,   -- суммарное число оценок по всем ивентам
  ADD COLUMN events_done   INT  DEFAULT 0;

-- Площадки организаций
CREATE TABLE venues (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  organizer_id UUID REFERENCES organizers(id) ON DELETE CASCADE,
  title        TEXT,
  address      TEXT,
  geom         GEOGRAPHY(POINT, 4326) NOT NULL,
  claim_radius INT DEFAULT 50,              -- метры, <= 150
  status       TEXT DEFAULT 'pending',      -- pending|verified|rejected
  proof_url    TEXT,
  created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX venues_geom_idx ON venues USING GIST (geom);

-- Реестр публичных зон (подтверждение не требуется)
CREATE TABLE public_zones (
  id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  kind   TEXT,                              -- park|square|street|embankment|...
  geom   GEOGRAPHY(POLYGON, 4326) NOT NULL,
  source TEXT                               -- osm|manual
);
CREATE INDEX public_zones_geom_idx ON public_zones USING GIST (geom);

-- Подтверждения чужих ивентов на площадке
ALTER TABLE events
  ADD COLUMN venue_id     UUID REFERENCES venues(id),
  ADD COLUMN venue_status TEXT DEFAULT 'none';  -- none|self|pending|confirmed|rejected

CREATE TABLE venue_confirmations (
  event_id    UUID REFERENCES events(id) ON DELETE CASCADE,
  venue_id    UUID REFERENCES venues(id) ON DELETE CASCADE,
  decided_by  UUID REFERENCES users(id),
  decision    TEXT,                          -- confirmed|rejected
  decided_at  TIMESTAMPTZ,
  deadline_at TIMESTAMPTZ,                    -- +48ч, для авто-эскалации
  PRIMARY KEY (event_id, venue_id)
);
```

Пайплайн создания ивента: гео-чек (`public_zones` → `venues`) → проставить `venue_id`/`venue_status` → если `pending`, создать `venue_confirmations` с `deadline_at` и уведомить владельца → фоновая джоба эскалирует просроченные в очередь модерации.

## Открытые вопросы
- Источник и качество `public_zones` для Астаны как пилотного города (полнота OSM по паркам/площадям/набережной; Алматы — следующим).
- Recency-вес рейтинга организатора — включать на старте или после набора данных.
- Споры «владелец отклонил легитимный ивент» — финальное слово у модератора (уже покрыто эскалацией).
