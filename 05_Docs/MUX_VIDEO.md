# Видео Mux — контракт и включение

Статус: код интеграции добавлен; аккаунт Mux, production-секреты и реальные загрузки не проверены. Фото и старые ролики остаются в текущем object storage / DB fallback. Миграция старых файлов автоматически не выполняется.

## Контракт

- `POST /media/presign` (JWT): для видео добавлены `eventId` и `sizeBytes`. При `VIDEO_PROVIDER=mux` событие обязательно. Ответ: `mediaId`, `uploadUrl`, `publicUrl=""`, `provider="mux"`. URL загрузки — временный секрет, не логировать и не хранить в черновике.
- Телефон делает PUT файла напрямую в `uploadUrl` отдельным клиентом без EventMap Bearer.
- `POST /media/confirm`: подтверждает передачу байтов, но **не** готовность видео. Для Mux сервер игнорирует клиентский `url`, проверяет владельца и неизменную привязку к событию. Возвращает `status=uploading|processing|ready|errored`, `provider`, `thumbnailUrl`; URL пуст до ready.
- Если ключ подписи воспроизведения отсутствует/неверен, готовое видео возвращается как `unavailable` без URL (fail closed). Это конфигурационная ошибка, не повод снова загружать исходник.
- `POST /videos`: добавлено поле `mediaId`. Для Mux публикация идемпотентна по этому ID, разрешена до окончания обработки. Только готовые ролики попадают в общую ленту. Событие должно совпадать с загрузкой.
- `GET /media/{id}`: состояние и свежие ссылки; доступ владельцу либо зрителю события. `GET /events/{id}/media` проверяет доступ к закрытому событию, возвращает статусы.
- `POST /webhooks/mux`: без EventMap JWT, обязательная проверка `mux-signature` над исходными байтами, окно 5 минут, дедупликация по ID события Mux в БД. Поздний `asset_created` не откатывает `ready`.
- Все новые Mux assets имеют **signed** playback policy. HLS и thumbnail подписываются сервером после проверки доступа; подписанные URL не сохраняются в БД. Лента `/videos/now` не включает закрытые события.
- Срок playback/thumbnail ссылки — 1 час. API-ответы с ними имеют `Cache-Control: private, no-store`; повторное открытие экрана обновляет ссылки. Доступ к ранее выданной ссылке сохраняется до истечения часа. Старые storage-файлы и фото имеют прежние публичные URL — эта интеграция не делает их приватными задним числом.
- Для закрытого события: автор, приглашённый пользователь (не отказавшийся) или одобренная сервером заявка. Самостоятельная отметка attendance не даёт доступ. Гость только по анонимной ссылке пока не получает видео.
- Ошибки: `VIDEO_OFF` 503 (не настроено), `VIDEO_PROVIDER_ERROR` 502 (ошибка Mux), `VIDEO_LIMIT` 429, `MEDIA_FORBIDDEN` 403, `MEDIA_NOT_FOUND` 404, `BAD_REQUEST` 422. Ошибка Mux не переключает загрузку молча в публичный storage.

## Настройка сервера

Включать только после обновления мобильного клиента и миграции V14:

```dotenv
VIDEO_PROVIDER=mux
MUX_TOKEN_ID=<API token ID>
MUX_TOKEN_SECRET=<API token secret>
MUX_WEBHOOK_SECRET=<secret конкретного webhook endpoint>
MUX_SIGNING_KEY_ID=<Video signing key ID>
MUX_SIGNING_PRIVATE_KEY=<base64 PEM из Mux или PEM с escaped newlines>
MUX_MAX_UPLOADS_PER_DAY=20
MUX_MAX_DURATION_SECONDS=120
```

API token: разрешения Mux Video Read/Write. Ключ подписи видео — отдельный RSA key, не API token. Все ключи только в секретах Render, никогда в приложении / Git / чате. Без `VIDEO_PROVIDER=mux` сохраняется прежний upload backend; в режиме mux неполная конфигурация запрещает новые загрузки.

Webhook URL: `https://<домен-бэка>/webhooks/mux`. Подписаться на `video.upload.asset_created`, `video.upload.errored`, `video.upload.cancelled`, `video.upload.timed_out`, `video.asset.ready`, `video.asset.errored`, `video.asset.deleted`. Вебхук и токены должны относиться к одному окружению Mux.

Лимит файла на клиенте 60 МиБ; сервер принимает заявленный размер до 64 МиБ. Заявленный размер не является жёсткой квотой Mux: клиент может отправить больше, а длительность известна после обработки. Для защиты бюджета обязательны лимиты/alerts аккаунта; лимит длительности блокирует публикацию, но уже выполненная обработка может тарифицироваться. Удаление брошенных/ошибочных assets и модерация контента — отдельный эксплуатационный шаг перед массовым запуском.

## Проверка перед включением

1. Применить миграцию, настроить секреты и webhook. Не отключать проверку подписи для отладки.
2. Загрузить настоящий ролик из создания события и из камеры. Убедиться в прямом PUT без Bearer и переходе processing → ready без повторной публикации.
3. Проверить HLS на Android и iOS, постер, повторное открытие экрана, ошибочный файл и потерю сети.
4. Повторить один webhook: в БД один ролик. Передать старую/поддельную подпись: 401, состояние не меняется.
5. Закрытый event: постороннему 403; приглашённому разрешено; в публичной ленте отсутствует. Подпись URL имеет ограниченный срок; ранее выданная ссылка действует до истечения TTL.

Документация провайдера: [Direct uploads](https://www.mux.com/docs/guides/upload-files-directly), [подпись webhook](https://www.mux.com/docs/core/verify-webhook-signatures), [signed playback](https://www.mux.com/docs/guides/secure-video-playback). Синтетические тесты не подтверждают реальную доставку из Mux или проигрывание на устройстве.

## Локальная проверка без ключей

Из корня проекта:

```sh
postman simulation run postman/simulations/mux/mux.sim.yaml --port 4027 --no-history --output ndjson
```

Из `04_Backend/server` во втором терминале:

```sh
MUX_SIMULATION_URL=http://127.0.0.1:4027/mux ./gradlew test
```

Симуляция локальная, на реальный Mux запросов не делает. Проверяет запрос direct upload и реакцию клиента на 401/503/HTML 502. Прочие методы mock возвращают 501. Без `MUX_SIMULATION_URL` только этот HTTP-тест пропускается; остальные локальные тесты выполняются. Поиск мока владельца и публичный приём webhook через Postman пропущены: CLI не авторизован. Не публиковать этот mock как реальный сервис.

`MuxRepositoryTest` использует H2 в PostgreSQL-режиме: это проверка запросов/переходов состояния, не доказательство применения Flyway V14 на PostgreSQL. `MuxRoutesTest` вызывает настоящие Ktor routes и проверку HMAC, но передаёт синтетические события.

## Результат проверки 05.11.2026

- Бэк: 33 теста, 0 ошибок/пропусков в запуске с локальной симуляцией. Из них 16 проверок Mux: криптография, signed playback, идемпотентность, права, квоты, Ktor routes и ошибки внешнего HTTP.
- Мобилка: Android `:androidApp:assembleDebug` завершён успешно. Desktop JVM tests: event UI 17, map UI 4, video data 1 — все прошли. Тест video data проверяет отсутствие EventMap Bearer в прямом PUT и передачу mediaId при 202 processing.
- Исправлены реальные заглушки в `AddMediaScreen` и галерее: выбор файла/превью/публикация, отображение обложки ролика и просмотр. Android-плеер умеет HLS, показывает загрузку/ошибку и не начинает загрузку соседнего ролика до показа.
- iOS-компиляция не завершена: при распаковке Kotlin/Native закончилось место. Удалён только неполный распакованный transform-кэш, созданный этой попыткой (163 МБ; восстанавливается Gradle). Нужны свободное место и повторная проверка iOS.
- В Render ничего не менялось. Секреты не задавались, аккаунт Mux не создавался, V14 на рабочей PostgreSQL не применялась. Реальное проигрывание Mux HLS и визуальный smoke-test на телефоне остаются обязательными.

Ограничения текущего клиента: файл передаётся одним PUT в foreground, без фонового/resumable upload; приложение держит выбранный файл в памяти. После закрытия приложения во время передачи может потребоваться новая загрузка. Retry публикации в форме события и «Добавить момент» сохраняет mediaId; камера при новом полном повторе загрузки может создать отдельный asset. Нужны очистка брошенных assets, серверная модерация и проверка бюджета перед публичным запуском.
