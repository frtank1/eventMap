# EventMap server (Ktor, Clean Architecture)

Бэкенд по слоям, PostgreSQL + Exposed, DI на Koin, JWT-аутентификация. Запускается локально через Docker; готов к деплою (Dockerfile).

## Слои (зависимости только внутрь)

```
presentation/   HTTP: routes + DTO (+мапперы domain→dto)   ──┐
        │ зависит от                                          │
domain/         model + repository (порты) + usecase          │  чистый, без фреймворков
        ▲ реализуется в                                       │
data/           Exposed-таблицы, DatabaseFactory, repo-impl  ──┘
security/       JwtService          di/  Koin-модуль          config/  env-конфиг
```

Правило: `domain` ничего не знает о Ktor/Exposed. `data` и `presentation` реализуют/используют порты из `domain`. Подмена БД или HTTP-слоя не трогает бизнес-логику.

## Запуск (локально, через Docker)

```bash
cd 04_Backend/server
docker compose up --build
```

Поднимутся Postgres + сервер на `http://localhost:8080`. При первом старте создаются таблицы и заливается сид по Астане.

Проверка:
```bash
curl http://localhost:8080/events
curl -X POST http://localhost:8080/auth/register -H "Content-Type: application/json" \
  -d '{"email":"a@a.kz","password":"123456","name":"Азамат"}'
```

### Без Docker (если Postgres уже стоит локально)
Создай БД `eventmap` (user/pass `eventmap`/`eventmap`) или переопредели env (`DB_URL`, `DB_USER`, `DB_PASSWORD`), затем:
```bash
./gradlew run
```

## Редактор зданий, этажей и помещений — 16.11.2026

Этот раздел описывает текущий срез; замечание выше о невозможности компиляции
относится к старой ревизии. Текущая реализация собирается и покрыта тестами.

**Открыть:** `/admin` → «Планы зданий» или сразу `/admin/venues` на адресе backend.
Используется существующий `ADMIN_KEY`. В production нужен HTTPS и собственный
непустой ключ, а не ключ локального тестового сервера. Новый редактор держит введённый
ключ только в памяти страницы, не сохраняет в storage и не включает в URL.

### Первый выпуск и обычная работа

Один раз выпустить этот backend: Flyway применит V15 (привязки событий), затем V16
(таблицы `venue_plans`, `venue_revisions`). После этого редактирование/публикация
не требуют ни нового APK, ни деплоя, ни перезапуска сервера. Мобильный читатель схемы
v1 из предыдущего среза уже совместим. До первого выпуска этих endpoint-ов редактор
на старом production-сервере отсутствует. Этот код сам ничего не развёртывает.

1. Ввести ключ, подключиться и выбрать здание. Для OSM-контура можно ввести точный
   `osm:way:<id>` / `osm:relation:<id>`. Не придумывать ID и не брать адресный node.
2. Добавить этаж, его название и порядок. Без рисунка этаж доступен текстовым списком.
3. «Добавить схему» → указать размеры локальной плоскости. Добавить помещение,
   назвать его, выбрать «Нарисовать контур», отметить углы и замкнуть контур.
   Другие помещения создаются аналогично. Сложный контур этажа можно импортировать
   в JSON (`plan.outline`). Размеры не являются широтой/долготой.
4. При необходимости открыть локальную PNG/JPEG/WebP-подложку до 8 MiB для обводки.
   Она растягивается на заданную плоскость, не сохраняется и не отправляется серверу.
   После сохранения/переключения этажа её нужно выбрать заново. Исходные PDF и
   изображения не становятся автоматически помещениями; публикуются векторы.
5. «Сохранить черновик» сохраняет работу в БД, но не меняет публичный план.
6. «Опубликовать» с подтверждением атомарно записывает новую revision и историю.
   В мобильном приложении открыть здание заново или нажать обновление плана.

Без опубликованных этажей приложение продолжает показывать события всего здания.
Серверный ресурс `venues/catalog.json` используется только до первых изменений
объекта в БД; новый деплой не стирает сохранённые черновики/публикации.
Бэкапы PostgreSQL включают планы и историю; локальная файловая система Render
для хранения планов не используется. Между инстансами нет кэша опубликованной схемы.

### Защита данных

- `expectedVersion` + блокировка строки не дают затереть чужое сохранение. При 409
  текущая форма остаётся у пользователя: экспортировать её и загрузить свежую версию.
- Публикуется только сохранённый черновик. Повтор старого запроса публикации получает
  409, не создаёт дублирующую ревизию. При сетевом таймауте сначала перезагрузить
  состояние: запрос мог успеть выполниться.
- Опубликованные ID этажей/помещений нельзя удалять/переименовывать/переносить между
  этажами. Иначе старые события указывали бы на исчезнувшее помещение. Для снятия
  рисунка сохранить этаж/комнату и очистить геометрию. Полное удаление действующего
  места с миграцией событий — отдельная, пока не реализованная операция.
- История показывает последние 20 версий; более старые снимки не удаляются. Кнопка
  истории только загружает снимок в форму, не публикует его. Если в новых версиях
  были добавлены ID, их нужно сохранить и при восстановлении старой геометрии.
- Ограничения схемы v1 остаются прежними: 32 этажа, 200 помещений на этаж/1000 на
  здание, 20 тысяч вершин, JSON-запрос ≤1 MiB. Данные проходят серверную валидацию;
  неизвестные поля отвергаются. Скрипты, удалённые URL и произвольные SVG не исполняются.
- Раздел использует общий административный ключ. Персональные роли, журнал действий
  по конкретным сотрудникам и согласование двумя модераторами не добавлены.
- Реальный план MEGA не включён. Тестовые схемы живут только в изолированной QA-базе.

### Воспроизводимая проверка

`./gradlew build` — backend и тесты, включая `VenueEditorTest`: доступ, черновик vs
публикация, неизменность истории, две конкурентные первые записи, stale/retry,
сохранность опубликованных IDs, плохой/слишком большой JSON и ресурсные заголовки.
Тест запускает настоящий SQL V16 на H2 в режиме PostgreSQL. Отдельный opt-in
`VenuePostgresMigrationTest` проверяет настоящие миграции Flyway на PostgreSQL:
V1–V14 → существующее событие → V15–V16 → повторный запуск без новых миграций,
сохранность события, constraint и две публикации для уже созданного reader.

Для него нужна **новая пустая локальная** PostgreSQL-база `venue_release_qa` с
пользователем `venue_qa` и тестовым паролем `local-venue-qa-only`. Тест принимает
только JDBC-адрес `127.0.0.1` с явным портом; при непустой базе прекращается,
не очищая данные. Без env явно пропускается:

```sh
EVENTMAP_VENUE_PG_TEST_URL=jdbc:postgresql://127.0.0.1:55439/venue_release_qa \
  ./gradlew test --tests com.eventmap.server.VenuePostgresMigrationTest --rerun-tasks
```

16.11.2026 этот тест прошёл на изолированном PostgreSQL 17 (1 тест, без пропуска).
Это не проверка production-базы, её резервной копии или экрана установленной
мобилки. Сам по себе успешный тест не означает, что релиз уже развёрнут в Render.

Для ручного UI-прогона (только на localhost, без основной базы):

```sh
./gradlew venueAdminPreview
```

Открыть `http://127.0.0.1:4891/admin/venues`, тестовый ключ `local-venue-test-only`.
Это не действующий ADMIN_KEY; он работает только в тестовом harness, который слушает
127.0.0.1, не запускает production Application.module и хранит данные в
`build/venue-editor-qa/plans.mv.db`. Перезапуск сохраняет тестовые планы.
Не развёртывать harness в production. Старые QA-проходы могли оставить файлы в
`build/venue-admin-preview*`; это изолированные тестовые базы, не данные пользователей.

Дополнительный end-to-end HTTP-тест запускается из `02_Code` при работающем harness:

```sh
EVENTMAP_VENUE_ADMIN_TEST_URL=http://127.0.0.1:4891/ ./gradlew :common:feature:event:data:desktopTest --rerun-tasks
```

`VenueAdminIntegrationTest` использует настоящий мобильный VenueRepositoryImpl/Ktor
и новый серверный API: сохраняет черновик, публикует, добавляет этаж и публикует снова
при том же сервере/клиенте. Без env тест явно пропущен. Записывается только синтетический
`osm:way:999999991` в локальном harness. Production, реальные планы, физический
телефон и развертывание на Render этим прогоном не проверяются.

Проверено в текущем срезе: backend `build` успешен (50 тестов: 49 прошли, один
существующий внешний Mux-тест пропущен); отдельный `VenueAdminIntegrationTest`
прошёл через реальный HTTP, без пропуска. В браузере пройдено: пустое здание →
этаж → помещение с нарисованным контуром → сохранение → публикация → изменение
названия помещения → повторная публикация → загрузка истории в форму → отказ от
несохранённых изменений → возврат актуальной версии. Опубликованные ID заблокированы
от изменения в UI. Скрин: `build/reports/venue-admin/published-plan.png`.
Все данные этого UI-прогона находятся только в QA-базе; это не настоящий план MEGA.
